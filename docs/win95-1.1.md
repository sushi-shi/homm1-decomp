# Windows 95 1.1 fork

This repository branches from `sushi-shi/homm1-decomp` master at
`f323b279` and targets NWC's May 7, 1996 Windows 95 1.1 executable.
The game and May 6 editor hashes are pinned in `config/retail/targets.json`.
The compiler remains VC4.0 with the inherited per-unit `/Zi /Gi` profiles and
`D:\Heroes` source paths. Runtime libraries remain WAIL32, SMKWAI32 and WING32.

## Address correspondence

`config/retail/win95-1.0-to-1.1.tsv` records the old and new RVAs of inherited
claims. The migration used normalized byte fingerprints, checked monotonic
link order, paired call targets, and vtable slots. Changed bodies were aligned
between anchors; conflicting operand pairs were checked against neighboring
references rather than resolved by voting. Data interiors were translated only
where the surrounding mapped references had the same displacement. The source
claims, generated initializer identities, MASM claims, function/data censuses,
and reviewed relocation referents all use 1.1 addresses. The runtime DNA census
was rerun against 1.1. Old scores were discarded and remeasured in strict mode.

The added function at RVA `0x072e57` is `ShutdownComError`, corroborated by
HoMM2 Buka 2.1's `SOURCE/comwin.cpp`. It sits between `init_anchor` and
`com_init`. It is not part of the preceding function's contribution.

For another comparison, the read-only discovery command is:

```sh
homm1 sema fid --old /path/to/old.exe --new /path/to/new.exe \
  --census /path/to/old/config/retail/functions.tsv --out build/fid.json
```

The census must describe the **old** image. Each result includes a fingerprint,
candidates, and its order bracket. Only relocation fields and decoded relative
branch operands are masked; a non-address immediate remains significant.
Fingerprints are candidate identities, not strict-match evidence. Referents and
branch destinations still require inspection. Nonmonotonic unique anchors stop
the command. No source or census is automatically rewritten.

## Source changes

- Chat in combat and network waiting moves from F1 to F2.
- Town entrance hover accepts the secondary trigger on adjacent cells.
- Loading a remote turn and starting a local human turn refresh the hover.
- Identify Hero clears when changing players, rather than once per day.
- Restoring saved new-game settings copies the first human's handicap to unset later human seats.
- Erasing an object clears its animation flag.
- Combat initialization flushes input and resets the pointer after music starts.
- Serial failures call `ShutdownComError`, which names the Win32 error,
  supplies connection suggestions, and invokes the existing shutdown path.
- The loading string and About dialog say 1.1.

## Validation and remaining work

`homm1 build` runs strict data comparison without unprovisioned identities.
`homm1 link` produces a candidate with no unresolved externals or duplicate
definitions, without `/FORCE`; the resource payloads match 1.1. The generated
README block is the score authority. No game runtime session was performed.

The changed serial routines and `NewGame` now match exactly after the review
below. `NewMap` preserves the 1.1 RNG order but is not byte-exact. Other
inherited matching work remains visible in the normal inventory.

Full `homm1 build verify` still reports the parent's existing failures in
`board`, `casts`, `compiler-artifacts`, and `dead-code`. A control run of
`homm1 verify check --no-readme` on the unchanged parent confirmed the same
findings. The floors and rules have not been relaxed. In particular, this fork
does not resolve the inherited cast recursion findings or CPU-speed assembly
policy finding.

`homm1 verify claim-size` also retains the parent's ten extent findings in
DIMMER, FINDPATH and SEARCH. The two additional 1.1 findings were corrected:
`army::FlyTo` and `soundManager::SwitchAmbientMusic` each grew by one byte
without moving the next aligned start. All inherited `VA` addresses were
audited against the migration table; the updated size claims include these
within-alignment changes.

Matching comments describing donor or February retail observations remain
historical evidence. For executable addresses use the current annotations,
retail tables and `homm1 sema`; translate old observations through the migration
table where needed.

## Changed-function review (in progress)

The review compares the February 1.0 executable with May 1.1, using the
target hashes above and parent `f323b279`. The complete per-census-entry
inventory is [win95-1.0-to-1.1-review.tsv](../config/retail/win95-1.0-to-1.1-review.tsv).
It includes the unchanged/address-translated entries as well as the changed
ones. Source matching remains strict, including data identities and addends.

The first byte-fingerprint pass is only discovery: HIGHLOW operands, relative
branches, inline jump tables, alignment, and compiler-generated EH continuations
must be checked separately. Comparing the modeled retail objects and their
ordered references adds cases that address masking alone hides. In particular,
an unchanged instruction can load the other side of a comparison, a different
term of a floating sum, or a changed string. The comparison found 51 inherited
functions to review, in addition to `ShutdownComError`.

The original census has inherited runtime entry omissions. Independent call,
pointer, prologue, and padding scans found no additional new game function.
That supports this review's scope; it is not a proof of an exhaustive census or
of all possible changes to unreferenced data. This report also does not claim
runtime play testing.

### Behavioral findings

The chat, hover, player-change, erased-object, combat-initialization, and serial
error changes described above remain supported by the retail comparisons.
Further inspection corrected three omissions in the initial migration:

- `NewGame`'s new handicap-copy loop belongs **inside** the saved-settings
  guard. The previous reconstruction ran it even without saved settings. The
  corrected branch destination and whole function now match exactly.
- `NewMap` consumes the ultimate-artifact spread rolls in **30, 20, 20** range
  order, rather than **20, 20, 30**, at both sites. The distribution of the sum
  is unchanged, but a fixed RNG state can produce a different result. The
  reconstruction now sequences the first roll explicitly. This preserves the
  observed order but introduces two bytes of compiler residue across the
  function; exact matching remains open.
- `CDStop` changes the MCI command from `stop CD` to `stop CD wait`.
  `CDShutdown` retains its separate `stop CD` command. The corrected CDStop
  literal and its reference now match.

`RVConversion` retains all seven weighted resource terms but changes their
floating accumulation order. Its source now follows the 1.1 order and matches
exactly. `ValueOfEventAtPosition` also changes floating-term order; its
remaining x87 association differences are still open and must not be dismissed
as behaviorally neutral. Reordering integer additions or mirroring a comparison
is a different category from reordering floating arithmetic or RNG calls.

`GiveExperience` has a diagnostic-data change: its `/Gi` line static is 1113,
formerly 1110. Assertion offsets remain +8 and +9. The corrected `#line`
directives reproduce the static without changing experience logic.

### Matching controls and remaining work

The four modified serial routines had matching API identities and control
flow, with differences in local frame placement. The VC4 `/Od` name-bucket
model predicted the corrections: `ioResult` in `com_rcv`, `commStatus` in
`com_init`, and declaration order for the tied `node`/`result` buckets in
`com_snd` and `comm_wrt_task`. Real-TU compiles make all four exact. These are
reconstructed local names, not claims of recovered original spellings.

For `NewMap`, all three simple placements of the 30-range call in the sum,
and grouping the two 20-range calls, emitted the old call order. Those probes
were removed. Explicit sequencing is retained for the observed RNG behavior;
its additional store/reload structure remains to be matched. A parenthesized
artifact-value sum in `ValueOfEventAtPosition` was also byte-flat and removed.

# Windows 95 1.2 fork

## Behavioral changes: 1.1 → 1.2

`-` is 1.1; `+` is 1.2. These compact examples omit surrounding code.
They describe changes observed in the two pinned retail executables, not
new features inferred from a version label.

### CPU detection uses Windows

`GetCPUType` (1.2 RVA `0x3c985`) now asks Windows for the processor type.
It returns family 3, 4 or 5 for 386, 486 or Pentium, and zero otherwise.
The existing caller still selects default movement speeds from that result.

```diff
-// Test EFLAGS and execute CPUID to determine the processor family.
+memset(&info, 0, sizeof(info));
+GetSystemInfo(&info);
+switch (info.dwProcessorType) {
+case PROCESSOR_INTEL_386: return CPU_FAMILY_386;
+case PROCESSOR_INTEL_486: return CPU_FAMILY_486;
+case PROCESSOR_INTEL_PENTIUM: return CPU_FAMILY_PENTIUM;
+default: return 0;
+}
```

### Smacker palettes are copied and converted

The new `SMACKW32.DLL` interface replaces `SMKWAI32.DLL`. The decoded header
uses `NewPalette` at offset `0x68`, `Palette` at `0x6c`, and the updated
rectangle fields. `smackManager::Main` copies 768 RGB bytes into the owned
palette buffer and converts each component from eight bits to six bits.
`ConvertSmackerPalette` at RVA `0x3d46d` is a new game helper.

```diff
-pPalette->m_data = selectedSmackerPalette;
+memcpy(pPalette->m_data, smack->Palette, 768);
+ConvertSmackerPalette((u8*)pPalette->m_data);
```

The helper performs `palette[i] >>= 2` for all 768 components. Conversion
runs after seeking to the intro frame, on each `NewPalette` notification,
and before the final fade. During playback the palette update now precedes
`SmackDoFrame`. The old alternate-palette selector and `SmackVolumePan`
calls disappear. The unused local `radmalloc`/`radfree` wrappers are removed.
The eight movie records retain their names and fade flags; the first four
change their preload flag for the new SDK:

```diff
-/* openFlags */ 0x20
+/* openFlags */ SMACK_PRELOAD_ALL  // 0x200
```

The `SmackM1`, `SmackM2` and `SmackM3b` log messages disappear; `SmackM2b`
remains. Track flags and function declarations follow the new runtime ABI.

### Digital audio releases and reacquires its device

Miles changes from `WAIL32.DLL` to `MSS32.DLL`. `WAVE_init_driver`
(RVA `0x74390`) requests the waveOut backend after validating device caps:

```diff
+AIL_set_preference(DIG_USE_WAVEOUT, 1);
```

`CDPlay` stops samples before starting a different CD track, after the
existing early return for an already playing track. `StopAllSamples`
(RVA `0x74a90`) stops/closes current playback, releases the digital device,
and attempts to reacquire it up to 20 times, waiting 5 ms before each try:

```diff
-// Bounded sample-service wait.
+AIL_digital_handle_release(m_digitalDriver);
+for (wait = 0; wait < 20; wait++) {
+    DelayMilli(5);
+    if (AIL_digital_handle_reacquire(m_digitalDriver))
+        break;
+}
```

`StopSample` (RVA `0x74b80`) retains the no-sound guard and `AIL_end_sample`,
but removes its music-stream service/wait loop. This also changes its inline
copies in `StartSample`, `SetMusicQuality` and `MemorySample`.
`PlayAmbientMusic` retains its own explicit 10 × 5 ms service/wait loop.

### Streamed samples use signed mono eight-bit PCM

`StartSample` (RVA `0x747e0`) still scans the filename suffix for `1`, `2`
or `4` to select the sample rate. The `6`, `8`, `M` and `m` format selectors
are removed; sample format is now fixed:

```diff
-AIL_set_sample_type(sample, sampleType | stereo, DIG_PCM_SIGN);
+AIL_set_sample_type(sample, DIG_F_MONO_8, DIG_PCM_SIGN);
```

### NetBIOS send processing gains timestamped diagnostics

`nb_thr_ctl` (RVA `0x520c2`) logs entry, each iteration and exit of its send
section. The queue operations and retry rules remain in place.

```diff
+LogInt("In SendSection Start", KBTickCount());
 while (keepRunning) {
+    LogInt("In SendSection", KBTickCount());
     // Existing send queue processing.
 }
+LogInt("Leaving SendSection", KBTickCount());
```

The executable grows from 715,776 to 726,016 bytes. Its entry point is RVA
`0x81770`; `.text` spans `0x1000..0x8c5a2`. The CRT begins at `0x7fde8`,

body matches establish that boundary. Vendor thunks precede the BASE library,
so the final thunk cannot establish the CRT boundary.

## Compiler and executable contracts

The port selects **VC4.1: CL 10.10.6038, LINK 3.10.6038**, retaining the
measured per-unit `/Gi` profiles. Original-media hashes, discriminating
real-function controls and release reproduction are documented in
[the VC4.1 controls](patterns/vc41-win95-1997.md). The recovered source paths
are `F:\H1w95src\Base` and `F:\h1w95src\source`; the fixed-path compiler
runner reads them from `config/units.toml`. Assertion filename strings and
line words are retargeted from retail evidence.

The new compiler bundle is `toolchain-win95-1.2-v1`, containing VC4.1,
MASM 6.11, WinG 1.0, DirectX 1 and RC/RCDLL/CVTRES. Its SHA-256 is
`b2430574160559ccfa9df604beb427955e5b641180265a3fc91e562ae87bcd63`.
Two independent package runs produced the same archive hash. Old toolchain
releases are unchanged. Proprietary game executables and runtime DLLs remain
local inputs, outside Git and outside the compiler archive.

The candidate is `build/exe/HEROESW.candidate.EXE`. Runtime deployment and
clean-source generation use `HEROESW.EXE`, `MSS32.DLL` and `SMACKW32.DLL`.
The retail image has **no exports**. Linking omits `/DEF` and preserves
`/STACK:0x10240,0x1000`; no `/FORCE` is used. All seven resource payloads are
identical to 1.1, including the unchanged “Version 1.1” About dialog.

## Mapping and complete body inventory

[Address correspondence](../config/retail/win95-1.1-to-1.2.tsv) records
function, global and interior-reference mappings with discovery evidence.
[The full body inventory](../config/retail/win95-1.1-to-1.2-review.tsv) covers
every old census start, including padding, removed wrappers and unresolved
runtime correspondence. It separates identical bytes, bodies differing only
in fingerprint-masked operands, and changed bodies. These are discovery
classes, **not strict matching scores or blanket proofs of behavior**.
The generated README block is the score authority for this target.

The inventory covers 1,284 old starts: 1,266 map to 1.2, four are padding,
two are removed allocators, eleven are removed Smacker thunks and one is an
unmapped CRT `_strncat` entry (`0x89b50`). Across the address ledger, all
4,180 mapped addresses move. Function deltas range from −392,655 to +441,408
bytes; the reordered units make a single average misleading. Body discovery
finds 173 identical byte sequences, 632 matching masked bodies and 461
changed bodies. These counts are cross-build discovery results, not scores.
There are 43 additional census starts outside mapped addresses: the palette
helper and 42 CRT starts. “Additional” includes newly discovered boundaries,
not necessarily new runtime functionality.

Whole-program link order changed, so no single address delta is valid.
Unique fingerprints anchor local translation-unit runs; decoded calls,
relocated data users, vtables and independently matched CRT objects resolve
the remaining correspondence. All source/header/vendor `VA`, `VA_COMPGEN`,
`DATA` and `RVA_DYNINIT` annotations with surviving identified counterparts
were retargeted, together with fixed-MASM claims and referent tables.

Independent direct-call and library scans add census entries beyond the
translated old list. The new palette converter is a game addition. The
`dimmerWidget` deleting destructor at `0x7eaa0` corresponds to old `0x7f410`:
it was missing from the old census, rather than newly added in 1.2.
All admitted vtable function targets are now census starts. CRT additions
and rewritten library bodies are identified separately in `dna_bands.tsv`.
The eleven old Smacker import wrappers disappear with direct IAT calls.

Four unused ADVMGR globals (`iThisMaxY`, `iThisMinY`, `USMsg`, `CDMsg`) retain
their source definitions but have no claimed 1.2 storage address: the old
unreferenced BSS placements are insufficient evidence after reordering.
This uncertainty is explicit; it is not resolved with a guessed address.

Initialized named data was compared after translating pointer identities
and checking pointed-to strings. The movie preload flags are the identified
value change; relocated tables and vtables keep their meanings. Mutable BSS
and unclaimed gaps are not a proof of complete data reconstruction.

## Validation and limits

The 69-unit build succeeds under the selected VC4.1 profiles. Candidate
linking resolves every external without forced linking. The strict data
identity and undefined-closure checks pass. Claim extents and the independent
vtable-target census were reviewed. No permutation campaign was run and
unchanged non-exact functions were not rewritten to chase byte equality.

A fresh 1.2 ledger is banked against this branch's source, without carrying
1.1 scores into different retail bytes. The final gate results and runtime
smoke-test outcome are recorded below. Compiler scheduling and register
allocation differences remain; object comparison is not a claim of a
byte-identical final executable or exhaustive gameplay validation.

Final gate run: `homm1 build verify` reports no score regressions and passes
vtable, enum-domain, label, line-directive, include-order, unique-name,
library-overlap, TU-order, undefined-closure, data-identity and review-claim
checks. It remains red on the same four gates as the saved 1.1 verification:
`board`, `casts`, `compiler-artifacts` and `dead-code`. The compiler-artifact
count decreases from four asm sites to three because CPU detection changed.
No floors or gate exceptions were altered. `homm1 verify claim-size` reports
zero findings; `homm1 audit usage` passes. Giten whole-tree and Gruntz audits
were run; their inventory warnings are not claims of complete donor parity.

The final PE contract check confirms identical sets of 203 imports, no export
directory, and stack reserve/commit `0x10240/0x1000`. The linked candidate is
726,528 bytes, so it is not a byte-identical copy of retail. Fresh archive
installation verifies all 363 pinned files; optimized INPUTMGR and `/GX`
HISCORE compile using that installed toolchain. Runtime deployment also
passes `homm1 play --dry-run` with local disc assets and the 1997 DLLs.
